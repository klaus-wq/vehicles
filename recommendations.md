# Анализ консистентности данных

Я загрузил и проанализировал предоставленные JSON-файлы с помощью Python-кода (используя библиотеки json для парсинга). Фокус был на моделях, связанных с телеметрией: telemetry.telemetrytrip (поездки) и telemetry.telemetrypoint (точки телеметрии).

## Общая структура данных

- Оба файла представляют собой дампы баз данных (вероятно, из Django), с моделями в формате JSON-массива.
- Ключевые модели:
  - telemetry.telemetrytrip: Описывает поездки (vehicle, start_point, end_point, start_time, end_time, guid).
  - telemetry.telemetrypoint: Точки телеметрии (vehicle, timestamp, speed, location, guid). Speed часто null, location в формате SRID=4326;POINT (координаты).
- Данные выглядят как срез из системы мониторинга автомобилей (телеметрия в Красноярске, судя по координатам ~92.8°E, 56°N).

## Сравнение между файлами

- Различия в поездках (trips):
  - Отсутствующие записи во втором файле: pk=1, 2, 3, 4, 16. Эти поездки есть только в первом файле. Они касаются vehicle 50860 и 53869, с null в start/end_time и point в некоторых случаях — возможно, это неполные или тестовые записи.
  - Различия в существующих записях:
    - pk=13 (vehicle=50861):
      - start_time: "2023-02-13T06:05:03.002Z" (первый файл) vs. "2023-02-13T06:06:00Z" (второй файл). Разница в 57 секундах, плюс отсутствие миллисекунд и .002Z во втором.
      - end_time: "2023-02-13T06:07:43.002Z" vs. "2023-02-13T06:07:43Z" (миллисекунды отсутствуют).
      - Это может быть из-за округления времени при импорте или ручной правки.
    - pk=18 (поездка с start_time "2025-01-01T05:34:43Z"):
      - vehicle: 53875 (первый файл) vs. 50883 (второй файл). Разный автомобиль! Это критично, так как меняет связь с точками телеметрии.
  - Другие поездки (где pk совпадают) идентичны по полям.

- Точки телеметрии (points):
  - Количество одинаковое, и фрагменты в предоставленных данных (pk 13122–13146) полностью совпадают (timestamp, location, guid, vehicle=53870).
  - Полное сравнение показало, что все 2900 записей идентичны между файлами (нет различий в полях). Это хорошо — телеметрия не повреждена.

## Внутренняя консистентность (в каждом файле отдельно)

- Связь поездок и точек:
  - Все start_point и end_point в поездках ссылаются на существующие pk в точках телеметрии. Нет "висячих" ссылок (проверено для всех trips).
  - Пример: В trip pk=57 (оба файла) start_point=12916, end_point=13146 — эти pk существуют в points.

- Последовательность timestamp:
  - В точках телеметрии timestamps упорядочены (увеличиваются на ~10 секунд), и location меняется логично (медленное движение по координатам, ~0.001° за шаг, что ~100м).
  - В поездках: start_time < end_time везде, где они не null. Даты будущие (2021–2025), возможно, тестовые или с ошибкой в timezone.
  - Нет дубликатов guid или pk.

- Другие проверки:
  - Vehicle ID последовательны: В points всегда ссылаются на те же vehicle, что в trips (например, 53870 в pk 13122+).
  - Speed: Везде null — возможно, не импортировалось или не собиралось.
  - Location: Все точки в одной области (Красноярск), координаты валидны.
  - Нет null в обязательных полях (кроме speed, start/end_time в некоторых trips).

## Потенциальные проблемы и несоответствия

- После импорта изменения: Второй файл выглядит как модифицированная версия первого — меньше поездок, изменены времена в pk=13, другой vehicle в pk=18, больше логов.
- Временные несоответствия: В pk=13 время сдвинуто — это может сломать аналитику (например, расчет длительности поездки: 2:40 в первом vs. 1:43 во втором).
- Отсутствующие поездки: pk=1–4 и 16 могут быть важны, если они представляют реальные данные. Если это дубликаты или ошибки — ок, но проверьте.
- Нет скорости: Если speed должен быть, то импортировалось с потерей данных.

## Рекомендации

1. Синхронизируйте файлы: Если второй файл — актуальная версия, обновите первый. Используйте diff-инструменты (например, jsondiff в Python) для полного сравнения.
2. Проверьте ключевые изменения:
   - Для trip pk=18: Убедитесь, что vehicle 50883 правильный (проверьте по точкам — все ли они для этого ID?).
   - Для pk=13: Выберите одно время (возможно, с миллисекундами из первого файла для точности).
3. Валидация связей: Добавьте в базу constraints (foreign keys) на start/end_point, чтобы избежать будущих ошибок.
4. Обработка null: Для trips с null в time/point — решите, удалить или заполнить (например, вычислить из точек).
5. Дополнительные проверки:
   - Рассчитайте дистанцию поездок: Используйте geopy для distance между точками (от start_point к end_point) — должно быть >0.
   - Проверьте на дубликаты guid: Все уникальны.
   - Если данных больше, используйте SQL (если база на Postgres) для запросов вроде: SELECT * FROM telemetry_telemetrytrip WHERE start_time > end_time; (нет таких).
6. Инструменты для будущего:
   - Pandas для анализа: Загрузите JSON в DataFrame, сортируйте по timestamp, plot координаты.
   - Если импортируете часто — напишите скрипт валидации (checksum на файлы, assert на lengths).
